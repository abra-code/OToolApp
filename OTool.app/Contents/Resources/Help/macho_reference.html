Mach-O header

Every Mach-O file begins with a fixed header that identifies the architecture and file kind, followed by a list of load commands. OTool's Headers tab shows the decoded header.

FieldMeaning
magicByte-order / 32- vs 64-bit marker (MH_MAGIC_64 = 64-bit, native order).
cputype / cpusubtypeTarget architecture — see CPU types.
filetypeWhat kind of file this is — see File types.
ncmdsNumber of load commands that follow the header.
sizeofcmdsTotal size, in bytes, of all load commands.
flagsBit flags describing the file — see Header flags.

Load commands

Load commands are directives, laid out right after the header, that tell dyld (and the kernel) how to map and prepare the file: where its segments go in memory, which libraries to load, where the symbol table and code signature live, and so on. OTool's Load Commands tab lists every one; selecting a row shows its fields with constants decoded.

LC_SEGMENT / LC_SEGMENT_64

Defines a segment — a contiguous range mapped into the process address space (e.g. __TEXT, __DATA, __LINKEDIT). Carries the segment's virtual address/size, its file offset/size, its memory protections, and the sections inside it.

maxprot/initprot are decoded as VM protections; flags as segment flags.

LC_SYMTAB

Locates the classic symbol table (nlist entries) and the string table that holds their names. The base of all symbol information.

LC_DYSYMTAB

The dynamic symbol table. Partitions the symbol table into local, externally-defined, and undefined groups, and points at the indirect symbol table the dynamic linker uses to bind stubs and pointers.

Dylib commands dependencies

Each names a dynamic library by install path, with compatibility and current version numbers. The variant says how it participates:

LC_LOAD_DYLIBA required library, loaded at launch.
LC_LOAD_WEAK_DYLIBWeakly linked — may be absent at runtime; its missing symbols become null.
LC_REEXPORT_DYLIBIts symbols are re-exported as if defined by this file (umbrella libraries).
LC_LOAD_UPWARD_DYLIBAn upward edge that breaks a mutual dependency cycle.
LC_LAZY_LOAD_DYLIBLoaded only when first used.
LC_ID_DYLIBThis file's own install name and version — present when the file is itself a dylib.

LC_LOAD_DYLINKER / LC_ID_DYLINKER

The path of the dynamic linker used to load the program (normally /usr/lib/dyld). LC_ID_DYLINKER appears in dyld itself.

LC_DYLD_INFO / LC_DYLD_INFO_ONLY

Compressed tables of dyld metadata: rebase opcodes (slide fixups), binding (resolve imports), weak and lazy binding, and the exported symbols trie. The _ONLY form means no equivalent classic relocation info is present. Superseded on newer binaries by chained fixups.

LC_DYLD_CHAINED_FIXUPS

The modern chained-fixups format. Rebases and binds are stored as compact chains threaded through the data itself, shrinking the file and speeding up launch. Pairs with LC_DYLD_EXPORTS_TRIE.

LC_DYLD_EXPORTS_TRIE

A trie (prefix tree) of the symbols this image exports, used with chained fixups instead of the export data inside LC_DYLD_INFO.

LC_UUID

A 128-bit build identifier. Debuggers and crash reporters use it to match a binary with the exact .dSYM that has its debug symbols.

LC_BUILD_VERSION

Records the target platform, the minimum OS (minos) the binary supports, and the SDK it was built with. May list the build tools and their versions.

platform → Platforms; tool → Build tools.

LC_VERSION_MIN_*

The older, platform-specific way to record minimum OS and SDK versions (one command per platform). Replaced by LC_BUILD_VERSION.

LC_SOURCE_VERSION

The version of the source code used to build the binary (a packed a.b.c.d.e number).

LC_MAIN

The program entry point: the file offset of main() (entryoff) plus an optional initial stack size. Modern replacement for LC_UNIXTHREAD.

LC_UNIXTHREAD / LC_THREAD

Initial CPU register state (including the entry point) for the program's first thread. LC_UNIXTHREAD also implies allocating a stack; older executables used this before LC_MAIN.

LC_FUNCTION_STARTS

A compressed table of function start addresses. Lets tools recover function boundaries (for symbolication and unwinding) even when symbols are stripped.

LC_DATA_IN_CODE

Marks ranges of non-instruction data sitting inside code sections (jump tables, constant islands), so disassemblers don't try to decode them as instructions.

LC_CODE_SIGNATURE

Points at the embedded code-signature blob (in __LINKEDIT): code directory, hashes, and the signature used to verify the binary's integrity and identity.

LC_ENCRYPTION_INFO / LC_ENCRYPTION_INFO_64

Describes a region encrypted by FairPlay DRM (App Store apps). cryptid 0 means the slot exists but the file is not currently encrypted.

LC_RPATH

Adds a runpath search directory. When a dependent library is recorded as @rpath/Foo.dylib, dyld tries each LC_RPATH path in turn to locate it.

LC_LINKER_OPTION

Linker flags embedded by the compiler in an object file (e.g. -lfoo, -framework Bar), so autolinking pulls in the right libraries.

LC_LINKER_OPTIMIZATION_HINT

Hints (mostly on arm64) that let the static linker rewrite certain instruction sequences into shorter, faster forms.

LC_SEGMENT_SPLIT_INFO

Relocation hints that allow segments to be split and re-slid independently when building the dyld shared cache.

LC_DYLIB_CODE_SIGN_DRS

Stores the Designated Requirements of the libraries this binary linked against, captured at build time for code-signing validation.

LC_TWOLEVEL_HINTS

A table of hints that accelerates lookups in the two-level namespace, where each undefined symbol remembers which library defines it.

LC_NOTE

A named region of arbitrary data carried in the file (identified by an owner string), used by tools to stash metadata.

LC_SUB_* (umbrella relationships)

Describe how umbrella frameworks are composed: LC_SUB_FRAMEWORK marks a sub-framework, LC_SUB_UMBRELLA/LC_SUB_LIBRARY name parents/children, and LC_SUB_CLIENT whitelists who may link a sub-framework directly.

Other & legacy commands

LC_FILESET_ENTRY identifies a member of a Mach-O fileset (e.g. a kernel collection). LC_ROUTINES (init routine address), LC_PREBOUND_DYLIB (prebinding), LC_SYMSEG, LC_IDENT, and LC_FVMFILE are legacy and rarely seen today.

Segments & sections

A segment (from LC_SEGMENT) contains zero or more sections — the finest-grained named chunks of a Mach-O file, such as __TEXT,__text (code) or __DATA,__data (writable data). Each section has an address, size, alignment, and a flags word that encodes its type plus a set of attributes.

Section types low byte of flags

The low 8 bits of a section's flags select one type:

ValueTypeMeaning
0x0S_REGULAROrdinary section (code or data).
0x1S_ZEROFILLZero-filled at load; occupies no file bytes (e.g. __bss).
0x2S_CSTRING_LITERALSPool of C string literals.
0x3–0x4S_4/8BYTE_LITERALSPools of fixed-size numeric literals.
0x5S_LITERAL_POINTERSPointers to literals.
0x6S_NON_LAZY_SYMBOL_POINTERSGOT-style pointers bound at load.
0x7S_LAZY_SYMBOL_POINTERSPointers bound on first use.
0x8S_SYMBOL_STUBSStub code for lazily-bound calls.
0x9–0xAS_MOD_INIT/TERM_FUNC_POINTERSC++ constructor / destructor pointers.
0xBS_COALESCEDSymbols merged by the linker (weak/inline).
0x11–0x16S_THREAD_LOCAL_*Thread-local storage data, pointers, and init.

Section attributes high bits of flags

BitAttributeMeaning
0x80000000PURE_INSTRUCTIONSContains only executable instructions.
0x40000000NO_TOCCoalesced section kept out of the table of contents.
0x20000000STRIP_STATIC_SYMSStatic symbols may be stripped.
0x10000000NO_DEAD_STRIPMust not be dead-stripped by the linker.
0x04000000SELF_MODIFYING_CODECode that rewrites itself (stubs).
0x02000000DEBUGDebug-only section.
0x00000400SOME_INSTRUCTIONSContains some instructions.

Example: 0x80000400 → Regular (pure-instr+some-instr), the typical flags for __TEXT,__text.

Linked libraries

OTool's Libraries tab lists the dynamic libraries this binary depends on (from the dylib commands) by install name. Common prefixes:

/usr/lib/…System libraries (served from the dyld shared cache).
/System/Library/Frameworks/…Apple frameworks.
@rpath/…Resolved against the binary's LC_RPATH entries.
@executable_path/… · @loader_path/…Relative to the main executable / the loading binary.

Symbols

OTool's Symbols tab lists the binary's symbol table — read with nm from LC_SYMTAB — alongside the indirect symbols (the stubs and GOT slots from otool -Iv). The Type column is the single-letter code nm prints for each symbol.

Symbol types Symbols · Type column

Letter case signals visibility: an uppercase letter marks an external (global) symbol the linker can see across files; the lowercase form is a local (file-private) symbol. U and C are always external.

UUndefined — referenced here but defined elsewhere; the dynamic linker binds it at load. These are the binary's imports.
T / tText — code, in a __TEXT section (typically a function).
D / dData — initialized data, in a __DATA section.
B / bBSS — zero-initialized data; occupies no space in the file.
CCommon — a tentative definition; the linker merges duplicates into one storage slot.
S / sSection — lives in some section other than text, data, or bss.
A / aAbsolute — a fixed value not associated with any section.
I / iIndirect — an alias whose value is taken from another named symbol.
-A debugger symbol-table (STAB) entry — debug info, not a normal symbol.
?A type nm did not recognize.
INDOTool's own tag for an indirect-table entry — a lazy/non-lazy pointer (GOT) or a call stub, from otool -Iv. The Indirect (stubs/GOT) filter shows just these.

OTool's Defined / Undefined (imported) filter keys off this letter: U is undefined, everything else counts as defined.

VM protections maxprot / initprot

A bitmask shown as rwx: read 0x1, write 0x2, execute 0x4.

0x5r-x — code (e.g. __TEXT)
0x3rw- — writable data (e.g. __DATA)
0x1r-- — read-only (e.g. __LINKEDIT)
0x0--- — no access (e.g. __PAGEZERO)

Segment flags LC_SEGMENT flags

0x1HIGHVMOccupies the high part of the VM space (legacy).
0x4NORELOCNo section in the segment is relocated.
0x8PROTECTED_VERSION_1Segment is encrypted/protected.
0x10READ_ONLYMade read-only after fixups are applied.
